# E0 -- AI-driven folding: mechanical verification and precision results

Generated by `run_e0.sh` (which compiles, runs and then calls `make_results.py`).
Do not hand-edit: re-run `./run_e0.sh` from this directory instead.

Design and the three proposals under test: `research/ai-driven-folding.md`.

**Role separation, per the memo's protocol.** The rewrites ("twins") and their
claimed coupling relations were produced by the PROPOSING agent and recorded in the
memo before any verification. This directory -- the equivalence checkers, the IR
encodings, the negative control and this report -- was built and run by a SEPARATE
VERIFYING agent, which treated the proposals as untrusted input: the twins are copied
verbatim into the C files (comments included) and are not repaired. Where a proposal
or a memo prediction fails, the failure is reported, not fixed.

No facts are injected anywhere in the precision leg. `eval/refanalyzer.py` is
imported unchanged; `precision.py` adds no domain, no transfer function and no hook.
Elapsed times are deliberately absent from all outputs; work is reported as input
counts.

## 1. Mechanical equivalence

Exhaustive enumeration, compiled `gcc -O2 -Wall -Wextra -std=c99`. Each driver prints
either `EQUIV: <case> <N> inputs checked, 0 mismatches` or the first mismatch with
both outputs, and exits nonzero on mismatch.

| case | suite / configuration | inputs checked | mismatches | status | level |
|---|---|---|---|---|---|
| 1 | all `unsigned int` | 4,294,967,296 | 0 | EQUIV | complete proof (2^32 = whole input space) |
| 2 | 8bit-exhaustive | 256 | 0 | EQUIV | complete proof at width 8 |
| 2 | 16bit-exhaustive | 65,536 | 0 | EQUIV | complete proof at width 16 |
| 2 | 32bit-exhaustive | 4,294,967,296 | 0 | EQUIV | complete proof at width 32 |
| 2 | 64bit-boundary | 31 | 0 | EQUIV | evidence only boundary set |
| 2 | 64bit-lcg-sample | 20,000,000 | 0 | EQUIV | sampling not a proof |

Exit codes: case1 `0`, case2 `0`, case3 `0` (0 = EQUIV).

**Measured intermediates, case 1.** The twin's own comments claim `t <= 0x1FFFE` and

`max_t = 0x1fffe`, `max_r = 0xffff` -- both claims confirmed, and the exact bound on `r` is
`0xFFFF`, one below the interval bound. That off-by-one is the subject of caveat C2.

## 2. Negative control (the mutant analog)

`equiv_case_neg.c` submits **proposal N**: case 1's twin with the second fold
dropped -- a plausible-looking off-by-one that keeps the twin's comment claiming the
value is already folded.

```
static unsigned short f_twin_N(unsigned int sum)
{
        unsigned int t = (sum & 0xffffu) + (sum >> 16);   /* <= 0x1FFFE */
        return (unsigned short)t;                         /* claims: already folded */
}
```

The verifier **rejects** it, with a concrete mismatch:

```
MISMATCH: case-neg first input sum=0x0001ffff f_orig=0x0001 f_twin_N=0x0000
REJECTED: proposal N rejected after scanning 4294967296 inputs; 2147450880 of them are mismatches
```

First mismatching input `0x0001ffff`: `f_orig = 0x0001`, `f_twin_N = 0x0000`. That is the smallest
input whose two 16-bit halves sum to `0x10000` (`0x0001 + 0xFFFF`), i.e. the first
carry-out of the single fold. In total 2,147,450,880 of the 4,294,967,296 inputs disagree, so the wrongness
is massive -- yet it is invisible on the first 131,071 inputs, which is exactly why a
mechanical check rather than spot-testing is the trusted base. Driver exit code `1`
(nonzero = rejected = the expected outcome for this file).

Per the memo's fail-safe: a rejected twin is discarded and the analysis is unchanged.

## 3. IR precision (eval/refanalyzer.py, unchanged, no injected facts)

Both C-to-IR lowerings of the bitwise operators are reported, because the choice
moves case 1 and neither choice is obviously the right one:

* **B ("bitwise-opaque")** -- every C `&`, `|`, `^`, `~` becomes the IR bitwise
  opcode, which refanalyzer sends to TOP (its documented imprecision F1). The
  strictest reading of "textbook interval domain".
* **M ("mask-as-modulus")** -- a mask `x & (2^n - 1)` on an unsigned operand becomes
  `modc x, 2^n`, because on unsigned values that mask *is* modular reduction. This is
  a syntactic, always-valid front-end rule. Every other bitwise operator, `~`
  included, still goes to the bitwise opcode: rewriting `~x` as `2^n - 1 - x` needs
  the range precondition `x < 2^n`, so it is not a syntactic lowering.

The two lowerings have identical *concrete* semantics; they differ only in which
abstract transfer the front end picks, and each is applied identically to a case's
original and twin. Casts (`(unsigned short)x`) are truncation, not a bitwise
operator, and lower to `modc` under both.

### Case 1 -- `csum_from32to16`, IR width 32, input = all 2^32

`rp` (original) and `r` (twin) are the value each `return` casts; `res` is the
returned `unsigned short`.

| form | `result <= 0x10000` | `result <= 0xFFFF` | returned value `<= 0xFFFF` | interval at the checked value |
|---|---|---|---|---|
| original | **PROVEN** | **PROVEN** | PROVEN | [0, 65,535] |
| twin, lowering B | **FAIL** | **FAIL** | PROVEN | [0, 4,294,967,295] |
| twin, lowering M | **PROVEN** | **FAIL** | PROVEN | [0, 65,536] |

**The memo's case-1 precision prediction is falsified.** It expected the original to
FAIL `check_range(result, 0, 0xFFFF)`. It PROVES it. The reason is structural, not an
accident of this analyzer: the original ends in `(unsigned)sum >> 16` at width 32, and
a right shift by a constant is exact in any interval domain that handles constant
shifts (refanalyzer says so in its own header note), so the result is bounded by
`0xFFFF` no matter how thoroughly the preceding rotate-add went to TOP. The check the
memo chose sits *downstream of a narrowing operation*, which hides the imprecision it
was meant to expose.

Consequently the case-1 twin is **verified but unhelpful**: equivalence holds over the
whole input space, so its verdicts do transfer, but it has no verdict the original
lacks. Under lowering M it is strictly weaker on the tight check (`r` reaches
`[0, 65536]`, so `r <= 0xFFFF` FAILs where the original PROVES it); under lowering B
it is weaker still. This is the memo's own "equivalent but unhelpful -> discarded"
branch, reached empirically.

### Case 2 -- nanopb ZigZag, IR width 32, analog width `n`, `value` in `[-2^k, 2^k)`

| analog width n | k | check | orig B | orig M | twin B | twin M | twin interval | note |
|---|---|---|---|---|---|---|---|---|
| 16 | 15 | `z <= 65,535` | PROVEN | PROVEN | **PROVEN** | **PROVEN** | [0, 65,535] | VACUOUS (k+1 = n: the bound is the whole unsigned analog type) |
| 16 | 14 | `z <= 32,767` | FAIL | FAIL | **PROVEN** | **PROVEN** | [0, 32,767] | non-vacuous |
| 16 | 13 | `z <= 16,383` | FAIL | FAIL | **PROVEN** | **PROVEN** | [0, 16,383] | non-vacuous |
| 8 | 7 | `z <= 255` | PROVEN | PROVEN | **PROVEN** | **PROVEN** | [0, 255] | VACUOUS (k+1 = n: the bound is the whole unsigned analog type) |
| 8 | 6 | `z <= 127` | FAIL | FAIL | **PROVEN** | **PROVEN** | [0, 127] | non-vacuous |

**This is the experiment's one real flip, and it is robust.** Wherever the check is
non-vacuous (`k + 1 < n`), the original FAILs and the twin PROVES, under *both*
lowerings. The original's negative branch computes `~(((T)value & mask) << 1)`: the
`~` has no interval transfer, so `z` collapses to the full analog range and only the
final truncation to `T` brings it back to `[0, 2^n)`. The twin's negative branch is
`2*(T)(-(value+1)) + 1`, affine throughout, so the input range propagates: at
`n = 16, k = 14` the twin's `z` lands on `[0, 32767]`, exactly `[0, 2^(k+1))` as the
memo predicted. The pattern-13 transport is *derived by the plain analysis on the
twin* instead of injected as a fact.

The memo named `k = 15` at a 16-bit analog. That is precisely the degenerate corner:
`[0, 2^16)` is the entire `uint16` range, so the check is satisfied by the declared
width alone and both forms PROVE it. The flip needs `k + 1 < n`, i.e. an input range
genuinely narrower than the type -- which is also the only setting in which the claim
"the interval result is exactly `[0, 2^(k+1))`" says anything.

*Input-range encoding, no facts.* `value in [-2^k, 2^k)` is two intervals of
two's-complement bit patterns and the IR's `input` yields one interval, so the entry
has two `input` sites, each followed by its own copy of the source's `if (value < 0)`
test; the two function bodies are shared and verbatim. The split is of the *entry*,
not of the function, and it is applied identically to original and twin.

### Case 3 -- `_find_first_bit`, IR width 16, 4 bits per word, size 16

| form | check | verdict | interval |
|---|---|---|---|
| original | `retval <= size` (`check_bound(ret, 17)`) | **PROVEN** | [0, 16] |
| original | *diagnostic*: `idx*BITS + __ffs(val) <= size`, **before** the kernel's `min` | **FAIL** | [0, 65,535] |
| twin | `retval <= size` (`check_bound(ret, 17)`) | **PROVEN** | [0, 16] |

**The memo's case-3 precision prediction is half right, and the half that fails is
the operative one.** The composition `idx * BITS_PER_LONG + __ffs(val)` really does
go to TOP -- the diagnostic row shows it reaching `[0, 65535]`, because the word
index `idx` is bounded only through `idx * BITS_PER_LONG < sz`, which refines the
*product*, not `idx`. But the kernel does not return that composition. It returns
`sz = min(idx * BITS_PER_LONG + __ffs(val), sz)`, and the `min` -- a plain branch --
re-establishes `retval <= size` by ordinary condition refinement. The original
therefore PROVES the memo's check without any relational fact, and the twin buys
nothing. The upstream author had already written the clamp that the fold was supposed
to supply.

This case is lowering-independent: neither form contains a mask, so B and M coincide.

## 4. Verdict transfer

Checks live in the original program; a PROVEN verdict on the twin's corresponding
check transfers to the original when the two are equivalent under the coupling
relation. Every relation here is plain input-output equality on function results, so
the check correspondence is the identity -- the memo's "check moved" failure mode
cannot arise in E0.

* **Case 1.** Equivalence is a complete proof over the entire input space (4,294,967,296 inputs),
  so every twin verdict transfers. No transfer is *useful*: the original already
  proves the memo's check, and the twin's tightest interval is strictly wider.
* **Case 2.** Equivalence is a complete proof at analog widths 8, 16 and 32, and
  evidence only at 64. At those analog widths, the twin's PROVEN verdict for
  `zigzagged < 2^(k+1)` transfers to the original, whose own verdict is FAIL. This is
  the FAIL -> PROVEN flip the architecture predicts, obtained with the reference
  analysis unchanged and nothing injected. **For the real 64-bit function the
  transfer is not yet licensed**: 2^64 was not enumerated, so the equivalence
  premise rests on the boundary set plus a sample. Closing that is an SMT job, not an
  enumeration job.
* **Case 3.** Equivalence is a complete proof for the two enumerated configurations
  (one 16-bit word, two 8-bit words, sizes 0..16). Transfer is available and buys
  nothing, since the original already proves `retval <= size`.

## 5. Caveats

**C1 -- which results are proofs and which are evidence.**

| result | status |
|---|---|
| case 1 equivalence | **complete proof**: 2^32 is the whole input space of `unsigned int` |
| case 2 equivalence at analog widths 8, 16, 32 | **complete proof at those widths** |
| case 2 equivalence at 64 bits (boundary set) | evidence only -- 31 hand-chosen corner inputs |
| case 2 equivalence at 64 bits (LCG sample) | evidence only -- deterministic sampling, **not** a proof; 20,000,000 of 2^64 is 1.1e-12 of the space |
| case 3 equivalence | **complete proof for the enumerated configurations** (word width 16 x 1 and 8 x 2, sizes 0..16); not a proof for `BITS_PER_LONG = 64` or unbounded word counts |
| negative control rejection | **complete**: the mismatch set was enumerated over all 2^32 |
| every precision verdict | a measurement of *this* reference analyzer on *this* IR encoding, not a claim about any production analyzer |

The reduced-width suites are "the same expression shapes at narrow types": every
operator of the source is reproduced at the analog width, including the `((T)-1) >> 1`
mask, the shift, the complement and the signed/unsigned conversions. That is evidence
the *shape* is equivalence-preserving, not a proof about the 64-bit instance.

**C2 -- case 1: the interval bound `0x10000` versus the exact bound `0xFFFF`. It
manifests, and it costs the twin the tighter check.** The driver measured
`max_r = 0xffff` over all 2^32 inputs, so `r <= 0xFFFF` holds concretely. The interval
analysis derives `r in [0, 65536]` instead: it sees `t in [0, 131070]`, hence
`t mod 2^16 in [0, 65535]` and `t >> 16 in [0, 1]`, and adds the two bounds
independently. Ruling out the joint corner `(65535, 1)` needs the low/carry relation
`t mod 2^16 = 65535 => t >> 16 = 0`, which no non-relational domain has. So the twin
PROVES `r <= 0x10000` and FAILs `r <= 0xFFFF`, exactly one unit short -- and since the
original PROVES `result <= 0xFFFF` outright, the off-by-one is what makes the twin a
regression rather than a tie on that check.

**C3 -- the lowering choice is load-bearing for case 1 and only for case 1.** The
case-1 twin's `check_range(r, 0, 0x10000)` is PROVEN under lowering M and FAIL under
lowering B; every case-2 and case-3 verdict is identical under both. A reader who
rejects lowering M should read case 1 as "twin strictly worse than original"; a reader
who accepts it should read it as "twin no better than original". Neither reading
yields a flip, so the conclusion for case 1 is lowering-independent even though the
individual verdict is not.

**C4 -- two of the memo's three precision predictions are wrong, in the same
direction.** The proposing agent predicted FAIL for the original in cases 1 and 3; the
baseline PROVES both, for concrete structural reasons (a constant right shift in case
1, the kernel's own `min` clamp in case 3). The baseline was not weakened to restore
the predicted flips. The general lesson is the memo's own: precision is measured,
never assumed -- including when the thing doing the assuming is the proposer.

**C5 -- case 2's check is vacuous at `k = n - 1`.** With the input range equal to the
whole signed analog type, `z < 2^(k+1)` is just `z < 2^n`, which the declared width
gives away. Rows `n16-k15` and `n8-k7` show both forms PROVEN for that reason and
should not be read as agreement. The reportable rows are the non-vacuous ones.

**C6 -- case 3's IR model is deliberately generous to the original.** Memory is not
modelled, so each `addr[idx]` fetch is a fresh nondeterministic `input` over the word
range, and `__ffs(val)` is handed its exact range `[0, BITS-1]` as an `input` rather
than being analysed. Both concessions help the original; the original still FAILs the
pre-`min` diagnostic and still needs the clamp.

**C7 -- what the equivalence checkers prove is C-abstract-machine equality of
results.** Original and twin are compiled in one translation unit at `-O2`; the
drivers compare returned values, not object code, and no undefined behaviour is
exercised (the twin's `-(value + 1)` is well defined at `INT64_MIN`, and `__ffs` is
only reached under `if (val)` in both forms). Equality of *observable results* is what
the coupling relation claims and what is checked.

**C8 -- the IR transliterations are themselves cross-checked.** `precision.py` runs
refanalyzer's concrete interpreter over every IR encoding and compares it against an
independent Python model of the C, on complete input windows (3 windows for case 1,
the full 8-bit domain for case 2, complete state enumeration for case 3): 21 checks,
all passing. Without this, a favourable precision verdict could come from a mis-transcribed
program rather than from the program.

**C9 -- no automation, no SMT, no production analyzer.** E0 verifies three
hand-recorded proposals by enumeration and measures one reference analyzer. It says
nothing about scaling the checker to SMT, about loops needing nontrivial coupling
invariants (all three relations here are input-output equality), or about automating
the propose -> verify -> analyze loop.
