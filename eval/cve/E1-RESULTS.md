## Summary

The survey (Part 4d) predicted this: the loop's two clamped copies (SITE1/SITE2) are genuinely safe but need the relation `fill_level + to_copy <= capacity` -- lost across an `add` by a plain interval domain -- to prove; the trailing fallback copy (SITE3) has no capacity check in the source at all and is the real bug. Measured here, not just argued:

* **baseline (plain intervals): 3/3 sites alarm** -- 2 false positives (SITE1, SITE2, both genuinely safe: 0 concrete violations each) plus the 1 true positive (SITE3).
* **with the R1 fold (`fill_level <= capacity` injected at SITE1/SITE2 only): 1/3 sites alarm** -- the 2 false positives are discharged (FAIL -> PROVEN), and the true alarm at SITE3 is untouched (still FAIL, exactly as soundness requires).
* **Soundness: 0 violations**, both configurations, checked against the complete concrete reachable state set (25 buckets, exhaustive, no budget exhaustion).
* **A concrete witness reproduces the real overflow** in this model: obuf starts empty, a 17-byte call arrives against a 16-byte capacity, the loop correctly fills the buffer to exactly capacity and leaves 1 byte over, `BIO_write` short-writes 0 bytes, and the trailing fallback appends that 1 leftover byte anyway -- landing 1 byte past the buffer's end.

**This is the POSITIVE outcome the design predicted**: fold reduces false alarms while preserving the true alarm, measured on real, source-cited, pre-fix CVE code rather than a synthetic catalogue example.

## Caveats -- what the model faithfully captures vs. abstracts

**What is faithful.** Every IR statement is commented against the real bf_lbuf.c line it models (see `cve_68160.py`'s `build_program()`). The branch structure at SITE1/SITE2 (`if (i >= llen) ... else ...`, bf_lbuf.c:141) is reproduced exactly, including the `>=`/`<` boundary. SITE3's check is genuinely unguarded in the source (no `if` at all before the memcpy) -- the check_bound the analyzer places there is the analyzer's own synthetic write-safety obligation, the same convention used throughout `eval/examples.py`, not something invented for this experiment or present in the C.

**What is simplified, and why (all labeled at the point of the simplification in `cve_68160.py`):**

1. **One buffering pass, not the full nested-loop control flow.** The real function has an outer `do...while (foundnl && inl > 0)` around an inner buffering `while`, plus a second write path for oversized chunks. This model collapses that to ONE pass: fill once, one (possibly short) `BIO_write`, then straight to the trailing fallback -- exactly the `!foundnl` exit path the survey traces and CVE-2025-68160 actually needs, not the fully general multi-iteration case. A faithful multi-iteration model would need a memory/string model (tracking `p` scanning for `\n` across a buffer) this tiny scalar IR does not have.
2. **`BIO_write`'s short-write return is modeled structurally, not as a literal-bounded `input`.** The IR's `input` opcode only accepts literal bounds, but the real bound (`0 <= return <= requested`) is against `fill2`, a runtime value. This is built as an explicit branch (the min-of-two-values idiom) so `drained <= fill2` is a genuine, concretely-enforced property -- NOT an unearned fact. **This bug bit during construction**: an earlier draft injected `drained <= fill2` as a bare fact without the branch, and `soundness()` caught it immediately -- a concrete state existed where a short-write return exceeded the buffer's fill level, wrapping `fill3` to a huge unsigned value. Fixed by adding the branch; recorded here per instructions ("investigate and report, do not hide").
3. **Two "structural" `lepair` facts are present in BOTH the baseline and with-fold configurations**, not just with-fold: `lepair(remaining, chunk)` (established by the SITE2 branch guard itself -- the same "guard transfers to the pointer bound" mechanism R1(c) describes) and `lepair(drained, fill2)` (BIO_write's own interface contract, now concretely enforced per point 2 above). Neither expresses `fill_level <= capacity` -- **that is the ONE fact that differs between the two runs**, injected at exactly SITE1 and SITE2, nowhere near SITE3. Without these two structural facts the subtraction sites would still be SOUND (they would simply widen to TOP), but SITE3's alarm would then be attributable to generic interval noise rather than the specific leftover-exceeds-what-the-short-write-freed mismatch that is the actual CVE mechanism -- keeping them on makes the true-positive demonstration attributable to the real bug, not to unrelated modeling slop. A reader who wants a stricter "zero facts at all in baseline" reading should note that omitting them does not change any of the three verdicts (checked by hand): SITE1/SITE2 still FAIL in baseline (their own imprecision is from the `fill+to_copy` add, upstream of these facts), and SITE3 still FAILs in both configurations (TOP is not more forgiving than a real bound).
4. **The fill-level entry state (`fill`) is fully free**, `input(0, CAP)`, rather than fixed at 0. `ctx->obuf_len` is a persistent struct field carried across calls to `linebuffer_write`; treating it as unconstrained is the honest most-general choice for a single-call model and is what actually exercises the interesting case (buffer already partway full going in).
5. **Buffer-write safety is checked as a fill-level bound (`fill_level <= capacity`), not a reconstructed per-byte memcpy index.** This IR has no memory/pointer model, so there is no `obuf[]` array to index into; checking the cursor itself against capacity is the same convention `eval/examples.py`'s own R1/pattern-16 examples use (`check_bound('p', bound)` on the cursor, not a simulated write).

**Sample-size honesty.** This is ONE canonical program (one CVE, one buffering pass, one parameter choice: `CAP=16, MAXCHUNK=24`), not a sweep. It measures whether the survey's Part 4d prediction is real for this CVE, on this model -- it is not a claim about false-alarm rates on production interval analyzers, nor about any other CVE in the survey (CVE-2022-3786 was flagged as the next candidate if the machinery generalizes cheaply; not attempted in this pass -- see the top-level task notes for status). The concrete state space (25 reachable-pc buckets under the chosen CAP/MAXCHUNK) is small enough for EXHAUSTIVE enumeration, not sampling, so the "0 concrete violations" claims for SITE1/SITE2 and the witness for SITE3 are complete proofs at this parameter choice, not evidence from a sample -- but they are still one parameter choice, not a sweep across capacities.
