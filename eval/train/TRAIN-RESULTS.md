Generated by `run_e3.sh` (which runs `train.py` and then calls `make_results.py`). Do not hand-edit: re-run `./run_e3.sh` from this directory instead.

Design: `research/E2-E3-design.md` ("E3 -- the training loop, driven by a security-bug database") and `research/folding-witnesses-and-learning.md` "The training loop, stated as an objective". `eval/refanalyzer.py` and `eval/examples.py` are imported UNCHANGED; the training loop is built on top, in this directory only.

## Summary

**Result: the shape-classification gate found ZERO folding-shaped cases in the sampled real corpus (an honest null, reported as-is, not routed around); the training-loop mechanics were then demonstrated on the design doc's sanctioned fallback corpus, where the false-positive rate on the 3 not-yet-learned shapes dropped from 18.8% to 0% on train and generalized to 0% on a held-out, different-parameter test split, with the bad()-proved-safe guardrail at 0 throughout.** All findings below are quoted verbatim from `train.py`'s own harness assertions (exit code 0 -- see `out/train.rc`).

## Corpus provenance (PART 1 of the raw output)

A slice of the NIST/SARD Juliet C/C++ test suite, CWE-121/122/124/126/127 (stack/heap overflow, underwrite, overread, underread), fetched via the `arichardson/juliet-test-suite-c` GitHub mirror at a pinned commit (`juliet_census.json`'s own `meta` block has the sha and fetch method). Every vulnerability-mechanism family across every `sNN` grouping in the five target CWEs was censused by directory listing -- 372 mechanisms, 27,593 files. Juliet's numeric flow-variant suffixes (01..84, `a`/`b`/`c` splits) vary control/data-flow plumbing (globals, threads, separate files, ...) for the SAME underlying flaw, never the arithmetic shape, per Juliet's own documented flow-variant taxonomy -- so classifying one representative file per mechanism (9 read in full; cited in `train.py`'s own comments) is representative of the whole ~65-86-file family, not just the one file read.

This is real, downloaded, labeled data -- not a guess at what Juliet contains -- used specifically for the shape-classification gate (design doc gate 1). It is a KEYWORD classification calibrated against the files actually read; the bucket rules and their calibration are in `train.py`'s own comments immediately above `def bucket(...)`.

## Reading PART 1 -- the null result, and why it is not a workaround

Zero of the 372 censused mechanisms are folding-shaped in the paper's technical sense (a plain interval domain losing precision to a stride>1 induction variable, a bijective/bit encoding, or a cross-variable relation -- exactly what a fold recovers). The dominant bucket (69% of files) is literal-vs-literal size mismatches (`memcpy(dst, src, 100)` into a 50-byte `dst`) -- already exact under a BASELINE interval analysis, no folding involved on either side. The second-largest (17%) superficially has a `for` loop, but every one read is stride-1 with a compile-time-constant bound, which a plain interval domain already gets exactly right (zero dead-band, `examples.py` sweep1's own closed form at stride 1) -- folding buys nothing there either. The remainder (11%) is a hardcoded or externally-sourced scalar used directly as an index/length with no induction or transform -- the design doc's own named Heartbleed shape, orthogonal to folding by construction. This matches the design doc's own anticipated finding almost exactly ("if most Juliet overflows are e.g. memcpy-with-tainted-length ... that bounds E3's reach and is itself a finding") and is consistent with `research/corpus-patterns.md`'s independent census of REAL production code (Linux kernel, OpenSSL, SQLite, lwIP, musl, curl), which DID find genuinely folding-shaped patterns (R1-R5) -- the gap is that Juliet is a synthetic, deliberately-simple, one-flaw-per-file microbenchmark built to test source/sink DATA-FLOW combinations, not induction-variable or bit-arithmetic precision, and so is a poor match for testing folding specifically, independent of how common folding-shaped bugs are in real code.

## Reading PART 2 -- the fallback corpus and what the metrics mean here

Per the design doc's explicit fallback provision, the training LOOP itself (propose, record-before-verify, mechanically verify, cache by shape, generalize, guardrail) runs against the 16 E0 catalogue patterns (`examples.EXAMPLES`, unchanged -- each mutant is a `bad()`, each canonical is the `good()`) plus 6 more held-out same-shape instances built via `examples.py`'s own parametrized builders (`_p1`, `_p13`, `_p16`, the same functions its own sweeps use) -- 22 pairs total, clearly labeled as the substitute corpus and smaller than a real slice, per the design doc's own instruction.

**Witness rate is 1.0 from iteration 0 and never moves.** This is a real property of this harness, not a bug: `refanalyzer.Concrete` exhaustively enumerates every reachable state of these small IR programs, so it finds every corpus bug's concrete violation independent of what fold_set is injected -- it is standing in for the "real under-approximate engine (symbolic execution / BMC)" the design doc allows for inexact folds, and at this program size that stand-in is unconditionally complete. The metric that actually moves with fold_set is the FALSE-POSITIVE rate on `good()` -- exactly the metric the design doc itself flags as the interesting one ("did it alarm on the bug is trivially 100% and is not the interesting metric"). E2 (`eval/witness/`) is where witness PRODUCTION -- not just corroboration -- is demonstrated directly by fold inversion, for the same three exact-fold shapes this experiment learns.

**A genuine bug was caught and fixed while building this**, and is worth recording: the first version of `evaluate()` cached the LEARNED fold as a frozen fact dict (computed once from the training instance's own parameters) rather than as a proposer function re-evaluated per case. Applied to the held-out test split, that stale literal fact was actually UNSOUND on the different-parameter instances (`soundness()` caught it immediately -- exactly the guardrail doing its job) and even produced one `bad()`-proved-safe case. The fix -- store the parametric proposer, not its output -- turned TABLE 3's generalization result from 2 soundness violations and 1 guardrail breach into a clean 0/0/0. This is itself a small, concrete illustration of the design doc's "cannot overfit into unsoundness" claim: the bug was a memorized-constant fold in disguise, and the guardrail caught it the first time it was checked against a different instance -- which is also exactly what TABLE 4's DELIBERATE overfitting illustration shows on purpose, using the SAME mechanism.
